# Marketplace Analytics 📊

> **Демонстрационные данные.** Проект работает полностью офлайн на сгенерированных вымышленных данных. Скачивать внешний датасет не требуется. Все метрики и закономерности демонстрационные; они показывают работу аналитики и не описывают реальный бизнес.

## Какую задачу решаем?

Как меняется GMV маркетплейса? Какова доля повторных покупок? Возвращаются ли покупатели в последующие месяцы? **Коррелируют** ли опоздания доставки с более низкими оценками покупателей? Каким клиентам могут подойти кампании по удержанию?

## Возможности

- Загрузка CSV с проверкой схемы, первичных ключей и цен и атомарным пересозданием базы SQLite
- 6 операционных таблиц + `order_mart` (ровно одна строка на `order_id`)
- Пять готовых бизнес-отчётов на SQL: KPI, ежемесячный GMV, доставка, повторные покупки и когорты
- Дашборд KPI: GMV, AOV, заказы, учитываемые в расчётах, покупатели и доля повторных покупателей
- Сравнение задержек доставки и отзывов; анализ наблюдательной связи, а не причинности
- Матрица удержания месячных когорт покупателей (месяц 0 — первая наблюдаемая покупка покупателя)
- RFM-сегментация и экспорт в CSV
- Фильтры по дате и штату, интерактивные графики Plotly и просмотр исходных данных витрины
- Воспроизводимый Jupyter-ноутбук, тесты pytest и CI на GitHub Actions

## Стек

`Python 3.10+` · `pandas` · `numpy` · `SQLite` · `Plotly` · `Streamlit` · `pytest` · `Jupyter`

**SQLite выбран осознанно:** для локального запуска не требуется настройка СУБД. SQL-запросы можно перенести в PostgreSQL с небольшими изменениями функций работы с датами. Проект работает на macOS (включая Apple Silicon), Linux и Windows.

## Быстрый старт (macOS / Linux)

```bash
unzip marketplace-analytics.zip
cd marketplace-analytics
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -e '.[dev]'

# Запустить дашборд: демоданные и база создадутся автоматически
streamlit run app.py
```

При первом запуске дашборд сам создаёт 3600 вымышленных заказов, CSV-файлы в `data/demo/` и базу `data/processed/marketplace.db`. При следующих запусках существующая база используется повторно. Внешние данные не нужны.

В Windows PowerShell активируйте окружение командой `.venv\Scripts\Activate.ps1`. Выполняйте команды из корня проекта.

Для повторного выполнения SQL-запросов, запуска тестов и открытия ноутбуков:

```bash
python scripts/run_sql.py 01_business_kpis.sql
python scripts/run_sql.py 05_cohort_retention.sql
pytest -q
jupyter lab notebooks/
```

Если исполняемый файл `marketplace-demo` отсутствует в PATH, используйте `python -m marketplace_analytics.demo`. Если исполняемый файл `marketplace-build` отсутствует в PATH, используйте `python -m marketplace_analytics.etl --source demo`.

## Данные проекта

Данные создаются автоматически при запуске дашборда. Для ручного пересоздания выполните:

```bash
marketplace-demo
marketplace-build --source demo
```

Эти команды заменяют демонстрационные CSV и базу. Генерация воспроизводима: по умолчанию используется `seed=42`. Команда `marketplace-demo --orders 5000 --seed 7` позволяет изменить число заказов и начальное значение генератора; после неё выполните `marketplace-build --source demo`.

Команда `marketplace-demo` создаёт вымышленные данные о заказах, покупателях, товарных позициях, платежах, отзывах и товарах. Затем `marketplace-build --source demo` проверяет CSV и собирает аналитическую базу SQLite.

## Определения бизнес-метрик

| KPI | Определение |
|---|---|
| Заказ, учитываемый в расчётах | Статус отличается от `canceled` и `unavailable` **и** есть хотя бы одна товарная позиция |
| GMV | Сумма `price` товарных позиций учитываемых заказов в BRL; без стоимости доставки; **не** чистая выручка и не прибыль |
| AOV | GMV / количество учитываемых заказов |
| Доля повторных покупателей | Доля уникальных покупателей с 2 и более учитываемыми заказами за выбранный период |
| Опоздание доставки | Фактическая дата завершённой доставки позже ожидаемой даты доставки (с точностью до календарного дня) |
| Когорта | Первый месяц с учитываемым заказом для `customer_unique_id` |
| Удержание M+n | Число уникальных покупателей, совершивших покупку в месяце n, / размер когорты; отображаются только наблюдаемые месяцы |
| RFM | Recency — число дней с последней покупки; frequency — количество заказов; monetary — GMV по ценам товарных позиций |

**Как избежать двойного счёта:** таблицы `items`, `payments` и `reviews` связаны с `orders` отношением «один ко многим». Перед объединением агрегируйте каждую из них до уровня `order_id`. Иначе один заказ с несколькими позициями, платежами или отзывами может многократно увеличить GMV.

**Важные ограничения:**

- Нет событий просмотров страниц, сессий и показов → нельзя оценить конверсию из просмотра в заказ, DAU или классическое удержание D1/D7.
- Правила отбора учитываемых заказов — аналитическое упрощение, а не правило бухгалтерского признания. Возвраты средств и товаров, комиссии и отмены заказов после первоначальной покупки могут потребовать дополнительной бизнес-логики.
- В график задержек и отзывов попадают только доставленные заказы с оценкой. На сравнения могут влиять смещение выборки, сезонность, качество товаров и состав перевозчиков.
- Когортный анализ требует полной истории покупателя. Вкладка когорт намеренно игнорирует фильтры дашборда, чтобы первая покупка не определялась заново в пределах неполного временного окна.
- RFM-сегментация **эвристическая**; это не обученная модель. RFM в дашборде рассчитывается по текущей отфильтрованной выборке, а опорная дата — следующий день после самого позднего заказа в ней.
- В демонстрационных данных искусственно повышена вероятность низких оценок у заказов с опозданием, поэтому **никогда не представляйте это как обнаруженную эмпирическую корреляцию**.

## Ноутбук и исследовательские вопросы

Откройте `notebooks/01_marketplace_analysis.ipynb`. Первая ячейка при необходимости создаст демоданные и базу. В нём воспроизводятся основные метрики, графики, когортная матрица, связь задержек с оценками и понятный набор бизнес-гипотез. Результаты иллюстрируют методы анализа на вымышленных данных.
